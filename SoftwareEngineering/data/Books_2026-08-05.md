I picked up this book because I wanted to better understand programming with AI

The term _agent_ can mean a lot of things.  The book focuses on what it calls

### Tools

The early parts cover tools, how to define them, and how to use and reuse them
in multiple agents.  Tools are just code that the LLM can trigger as part of
answering a query.  When the tools are strongly typed, for example with
parameter and return types or Zod schemas, the LLM can use them more
effectively.  But tools are code in the same language and executable that is
calling the LLM.  If two agents written in two different languages need the same
tool, you need to provide an implementation of the tool in both languages.

This is where MCP comes in.  You put the tools in a separate executable and use
the Model Context Protocol to call them.  The protocol is language agnostic.
Now, you have a single implementation of the tool that is accessible by agents
in different languages.  The tools don't even have to be in one of the agents'
languages.  There are existing MCP servers for many common third-party services,
like Slack or Notion or Google Calendar.  You can run your own copy of the MCP
server behind your firewall with your own access keys, or in some cases you can
use public MCP servers maintained by these third-party services.

But all this comes at a cost.  Tool descriptions, both internal tools and
external tools in MCP servers, become part of the prompt to the LLM, using up
precious context space and input tokens.  An MCP server may want to expose many
related tools, even if you only need one of them.  If your organization has
already standardized on a specific implementation language, it may be worth it
to have a library of tools in that language and only add the ones you
specifically need to any given agent.

### Layered Model

The book uses a layered model to describe the various capabilities of agents.
Agents have layers.  At the core is the _persona_ that guides the overall
purpose of the agent, usually via the `system` prompt.  Then, there are tools
and descriptions of actions the agent can take.  On top of that, the _reasoning_
layer tells the agent how to iterate to solve a problem and what to do in each
part of each iteration.  Long-lived agents will use a _memory_ layer to persist
information across iterations or even across runs of the agent process.
Finally, the more sophisticated agents with use a _feedback_ layer to
self-evaluate and double-check their work.  Oftentimes, the functionality of
each layer can be in separate cooperating agents.  This keeps each agent small
and dedicated to a single task, which is easier to reason about and debug.

> An agent is a system built around an LLM, combining the model with tools,
> memory, orchestration logic, and the ability to interact with an environment.
> The LLM is the reasoning component. Everything else turns that reasoning into
> work that affects the world.
> <footer>p. 139</footer>

I have been building software systems for many, many years.  I've been through
design patterns and REST APIs and microservices.  Each time, you specify the
computing logic in a programming language with very precise syntax and idioms.
I was surprised by the use of <del>English</del> natural language to tell the
LLM what logic was expected.

### Agents

All the code examples are in Python.  While I don't particularly care for
Python, its compact syntax makes it easy to read the code without getting lost
in convoluted syntax.  Since a lot of agents get they logic from natural
language descriptions, it is useful to keep syntax and code to a minimum so they
do not distract from the main point.

Here is a minimal example of an agent.  It takes unstructured text as input and
outputs unstructured text (hopefully Markdown).

    research_agent = Agent(
        name="Research Agent",
        instructions="""
            You are a research assistant.
            Your role is to find research sources.
        """,
    )
    
    goal = "..." # The prompt to the agent, what the user wants the agent to do
    
    result = await Runner.run(research_agent, goal)

All the logic is in the `instructions` string.

This example outputs unstructured text, but if we want to make decisions based
on that output, it is better to require structured output using some type or
some form of schema.  For instance, if we want the agent to classify some data,
it is better to require numerical scores as output so we can compare them to
thresholds and decide what to do next.

If we want more complex behavior from the agent, we just extend the
`instructions` string and tell it what we're expecting and how to go about doing
it.

Here is a later example:

    agent = Agent(
        name="Support",
        instructions=("Use ONLY retrieved context; cite chunk ids; if absent
            say 'I don't know'."),
        tools=[retrieve, remember],
    )

### Coordination Patterns

The book describes many ways for agents to collaborate together: flow,
hub-and-spokes, hierarchy.  It talks about orchestration, when one agent
explicitly drives the collaboration, versus collaboration, when there is no
clear leader and coordination is an emergent property.  It reminded me of the
discussion of orchestration versus choreography with microservices and sagas,
which also revolve on an explicit leader or emergent coordination.

Some of these discussions remained very high-level.  I would have liked more
concrete examples.  Late in the book, some of the examples finally connect to
the issue of coordination, but it is very late and hard to relate back to the
discussion.

### Miscellaneous Topics

There is a very good example of RAG and the different types of search.  I liked
the description of vector databases how they determine the proximity of topics.
It compared it to other types of search using graph databases and relational
databases.

The bit trying to relate agent "memory" to human cognitive neuroscience didn't
land for me. Not sure why agent would care about "sensory memory" as opposed to
image/video just being a different format of data. A lot of the integration is
done in prompts, but the discussion lacks the subtleties of telling the LLM when
to use what tool. (I guess that changes quickly as models evolve.)

The book does a better job when it maps failings or limitations of simpler
agents to cognitive deficits. It uses theory from **Minsky** (Society of Mind
about small agents collaborating together), **Baars** (Global Workspace Theory
about how the agents communicate through a shared cognitive workspace), and
**Kahneman** (System One, fast and automatic, versus System Two, slow and
deliberate) to fill in the gaps.  The book builds example where that exemplify
these theories.  I wonder if it might have been better to introduce these ideas
near the beginning and reference them throughout the book.  The author might
have lost more pragmatic readers, though.

The final examples solve some sophisticated use cases, like customer support,
RAG, and a research systems that can decide between multiple sources as needed.
